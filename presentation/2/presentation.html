01 · Introdução

O que é o FdF?

Um visualizador wireframe que transforma uma matriz de inteiros — o mapa de alturas — em um modelo 3D interativo desenhado linha a linha.

Em uma frase

"Cada número é a altura z de um ponto (x, y); o programa conecta vizinhos com retas e projeta tudo em 2D."

Por que importa?

Primeiro contato com pipeline gráfico real: parsing, transformações afins, projeções, clipping e rasterização — tudo do zero, sem GPU.

02 · Contexto

"Fil de fer" — fio de arame

Em francês, fil de fer significa "arame". Em computação gráfica, é o nome dado ao modelo wireframe: representação de um sólido apenas pelas suas arestas.

A técnica precede a renderização sólida e foi padrão em CAD e jogos dos anos 80 — barata em CPU, expressiva o suficiente para revelar topologia e relevo.

“

"Você verá, na imensidão da paisagem, somente o esqueleto que a sustenta."

04 · Entrada

Formato do arquivo .fdf

Texto simples: cada linha é uma fileira da malha; cada token é a altura z. Cor opcional após vírgula.

maps/pyramide.fdfplaintext
 1  0  0  0  0  0
 2  0  5  5  5  0
 3  0  5 10,0xff00aa  5  0
 4  0  5  5  5  0
 5  0  0  0  0  0
Regra 1. Todas as linhas precisam ter o mesmo número de colunas.
Regra 2. Cor é hexadecimal opcional após ,.
Regra 3. Alturas podem ser negativas (relevo abaixo do plano).
05 · Arquitetura

Pipeline de renderização

Cada frame percorre seis estágios — do disco ao framebuffer:

1

→
2
Transform
transform*.c · escala, rotação, translação
→
3
Project
projection.c · 3D → 2D
→
4
Clip
clipping.c · Cohen–Sutherland
→
5
Rasterize
bresenham.c · linhas em pixels
→
6
Blit
render.c · framebuffer → janela

Tudo roda na CPU, sem aceleração 3D. O custo é O(N · M) linhas por frame, onde N×M é o tamanho do mapa.

O coração do código

Quatro structs organizam todo o estado da aplicação:

include/fdf.hC
typedef struct s_point { float x, y, z; int color; }      t_point;

    int     color_palette;
} t_camera;
typedef struct s_fdf  { void *mlx_ptr, *win_ptr; t_img img; t_map map; t_camera camera; } t_fdf;

Cada ponto carrega sua própria cor (vinda do arquivo ou calculada por gradiente de altura).

07 · Rasterização

Algoritmo de Bresenham

O problema: dado dois pontos com coordenadas inteiras, qual a melhor sequência de pixels que aproxima a reta entre eles?

Bresenham resolve isso usando apenas inteiros — sem ponto flutuante, sem divisões — calculando o "erro" acumulado a cada passo no eixo dominante.

  • Trata 8 octantes (combinações de sinal e inclinação)
  • O(max(Δx, Δy)) por linha
  • Implementação em bresenham.c e bresenham_octantes.c
src/bresenham.c (esquema)C
while (b.error * 2 >= -b.delta_y)
{
    update_image_pixel(img, x, y, color);
    if (x == p2.x && y == p2.y)
        break;
    e2 = 2 * b.error;
    if (e2 >= -b.delta_y) {
        b.error -= b.delta_y;
        x += b.xi;
    }
    if (e2 <= b.delta_x) {
        b.error += b.delta_x;
        y += b.yi;
    }
}
08 · Projeção

Projeção isométrica

Três eixos a 120° entre si, todos com mesmo foreshortening. Sem perspectiva — paralelas ficam paralelas.

Fórmula

x' = x·cos(α) + y·cos(β) + z·cos(γ)
y' = x·sin(α) + y·sin(β) + z·sin(γ)

α = 30°    β = 150°    γ = -90°

Os ângulos vêm direto de ANG_30_RADIAN, ANG_120_RADIAN em fdf.h.

Trecho real

src/projection.cC
angle_x = ANG_30_RADIAN;
angle_y = ANG_30_RADIAN + ANG_120_RADIAN;
angle_z = ANG_30_RADIAN - ANG_120_RADIAN;
line->p1.x = p.x*cos(angle_x)
           + p.y*cos(angle_y)
           + p.z*cos(angle_z);
line->p1.y = p.x*sin(angle_x)
           + p.y*sin(angle_y)
           + p.z*sin(angle_z);
09 · Projeção

Projeção em perspectiva

Pontos mais distantes da câmera ficam menores: divide-se x e y pela distância em z ao plano focal.

x' = (x · f) / (z − depth)
y' = (y · f) / (z − depth)

Antes da divisão, é preciso cortar o que está atrás da câmera — caso contrário a divisão por z negativo "explode" o ponto pra fora da tela.

src/projection.cC
z1_distance = p1.z - depth_z;
z2_distance = p2.z - depth_z;
camera_clipping(line, &z1_distance, &z2_distance);
if (!line->show) return;
if (z1_distance != 0) {
    p1.x = (p1.x * focal_length) / z1_distance;
    p1.y = (p1.y * focal_length) / z1_distance;
}
10 · Recorte

Cohen–Sutherland clipping

Cada ponto recebe um código de 4 bits (outcode) indicando em qual região está em relação à viewport:

BitPosição
0001esquerda do viewport
0010direita
0100abaixo
1000acima
0000dentro (visível)

Decisão rápida

  • code1 | code2 == 0 → linha 100% dentro, desenha direto
  • code1 & code2 != 0 → 100% fora, descarta
  • caso contrário, recorta na borda mais externa e repete

Implementado em src/clipping.c junto com o near-plane clipping da câmera (corte em z).

11 · Estética

Sistema de cores

Quatro paletas selecionáveis em runtime (C). Cada linha pode ter cor própria do arquivo, ou um gradiente é calculado pela altura relativa (z − min_z) / (max_z − min_z).

P0 · Default
P1 · Violet → Black
P2 · Magenta → Cyan
P3 · Green

A interpolação é feita canal a canal — delta_r, delta_g, delta_b em t_color.

15 · Build & run

Compilando e executando

Local (Linux)

shellbash
$ make
$ ./fdf maps/42.fdf
$ ./fdf maps/julia.fdf
$ make clean && make re

Flags: -Wall -Wextra -Werror. Linka contra libft, libmlx, libm, libbsd, X11, Xext.

Docker (qualquer host)

shellbash
$ docker compose up --build
# Ubuntu 20.04 + X11 forwarding
# janela renderizada no host

O Dockerfile instala libxext-dev, libbsd-dev e libx11-dev; o compose faz bind do $DISPLAY e do socket X.

16 · Aprendizados

Onde foi difícil

⚠

Divisão por zero na perspectiva

Pontos exatamente no plano focal explodiam. Solução: near-plane clipping antes da divisão.

↻

Ordem de transformações

Rotação antes de translação dá resultado diferente do contrário — descobri isso da forma cara.

▥

Mapas grandes & performance

100-6.fdf tem 600 pontos. Cuidado com O(n²) escondido no parser.

⊞

Linhas fora do viewport

Sem clipping, MiniLibX escreve fora do framebuffer e segfaulta. Cohen–Sutherland resolve.
